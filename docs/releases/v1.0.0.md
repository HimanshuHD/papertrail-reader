## Release notes

PaperTrail's first major release is a local-first browser PDF reader. Select local files or a folder, browse the library and read without uploading document bytes.

- Responsive Home with Go to app, a production empty reader state and native SVG identity.
- Directory/file selection with supported-browser picker detection, fallback inputs, incremental discovery, cancellation, tree browsing and refresh. Each PDF uses one title or filename label with ellipsis/full-label access.
- A draggable/resizable library and independently scrolling PDF/utility panes within the browser viewport.
- PDF.js continuous rendering, selectable text, page count/jump/previous/next, zoom, fit width/page, contents/outlines, fullscreen and keyboard help.
- Case-insensitive text search with wrapping results, safely marked terms, up to 50 Unicode characters before/after a match and exact selected-occurrence highlights in the PDF.
- Buffered canvas replacement, stable reading-point anchors and page tracking after large scrollbar jumps. Large documents open without rasterizing every page first; distant full-resolution canvases are released and reusable previews have bounded memory.
- Light/dark preferences, accessible icon controls, focus restoration, reduced-motion handling, centered loading feedback, polished panels/popovers and compact footer.
- Production main CI/publication, manual numbered PR previews, source SHA/branch links and preview retirement. Ordinary Frontend CI remains browser-free; browser acceptance is explicit.

Major implementation/acceptance PRs: #59/#60/#65 PDF core/utilities; #66 viewport; #70/#71 identity/library; #73/#77 toolbar/lifecycle; #83 production empty state; #90 rendering/performance; #96 labels/scrolling; #97 loading; #98 controls/footer; #101 search; #99/#102 documentation evidence.

## Scope boundaries and known limitations

- PDF-only. EPUB selection gives an accurate future-release message; #12 remains in Roadmap 2.
- Search and selected-match highlighting require a searchable text layer. Scanned/image-only PDFs are viewable but no OCR is provided. Password entry is not implemented; password-protected files produce an explicit recoverable limitation message.
- Reading positions/bookmarks, recents, annotations, tabs/session restoration, exports and Tauri are not included (#13–#18/#4).
- File access requires user selection/permission. Native directory handles depend on HTTPS, user activation and browser support; folder/file input fallbacks remain available. Refresh can re-read supported handles; this release does not promise automatic retained access after reload.
- Document bytes/metadata/text are processed client-side. The application/site still downloads its static assets/worker; this is not a promise of offline/PWA support or malicious-PDF certification.
- Large-document regression uses a synthetic 1,001-page PDF. It proves lazy opening/distant jumps and bounded active canvases; it does not benchmark all image-heavy or malformed PDFs or impose a universal loading SLA. Mixed-size distant page slots are initially estimated until approached.
- Formal broader browser/device certification, advanced versioned promotion/rollback, queued-publisher recovery and docs-only workflow event filtering remain #28/#32/#44/#100 under #78. Docs-only main merges currently may create a publisher run whose deployment steps skip; tagging this version does not refine that policy.

## Release procedure

1. Review the version/release-record PR. Package version, both root lockfile version fields, release notes and footer source agree on 1.0.0. Ensure final fast CI and explicit Browser E2E are green; any subsequent runtime edit requires a new applicable regression.
2. Merge the reviewed PR to main. Record its exact merge SHA as RELEASE_SHA. Wait for main Frontend CI and Publish website to succeed; verify the published source comes from that main CI artifact. Tracker-only descendants do not change the reviewed tag target.
3. Check production build.json and deployment.json against RELEASE_SHA/source CI. Open both Home and #/app: footer must show Production · v1.0.0 with linked full SHA, and manual preview identifiers must not appear in production. Verify document opening, page navigation, zoom/fit, search selection, themes and a large scrollbar jump after refresh. Confirm the release PR preview is retired if it was published.
4. Only when those gates pass, create an annotated v1.0.0 tag at RELEASE_SHA and a stable GitHub release with the notes in this file. There is no release/tag-specific deployment workflow in this increment; main merge publication deploys the website before tagging. Do not tag 0.1.0 or a PR head that differs from the deployed reviewed merge.
5. Record tag SHA, release URL/date, main CI, publisher, production source/version, smoke results and any assets below. Update the release ledger to Released; reconcile #80/#1 as completed. Roadmap 2 begins afterward.

For an authenticated maintainer checkout, once RELEASE_SHA is the verified 40-character release merge SHA:

```bash
git fetch origin main --tags
git show "$RELEASE_SHA":package.json
git diff "$RELEASE_SHA" origin/main -- src package.json package-lock.json vite.config.ts
git tag -a v1.0.0 "$RELEASE_SHA" -m "PaperTrail v1.0.0 — first browser PDF release"
git push origin refs/tags/v1.0.0
gh release create v1.0.0 --verify-tag --title "PaperTrail v1.0.0" --notes-file docs/releases/v1.0.0-notes.md
```

Inspect any diff before proceeding; never substitute an unexplained latest main head. [v1.0.0-notes.md](v1.0.0-notes.md) contains the user-facing release notes and limitations from this record. GitHub's automatic source archives accompany the release. The website is delivered through Pages; desktop installers/npm publication/PDF document uploads are not release assets for this scope. If a tag already exists, verify its target rather than force-replacing it.

## Recovery / fix-forward

Before tagging: stop the release if main CI/publication/source/version or smoke checks fail; fix through a reviewed PR and revalidate the final target. Last known good application source before version preparation is 77b8f31 (v0.1.0). Use the normal reviewed main revert/fix workflow and publishing checks; do not push generated pages-state files manually.

After tagging: preserve v1.0.0 and its audit record. Prefer a validated v1.0.1 fix; if needed, revert the specific faulty application change through a main PR and verify production recovery. This is operational guidance, not an implemented immutable release-artifact rollback/promotion system (#32).
